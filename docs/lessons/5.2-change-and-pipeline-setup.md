# 5.2 変更要求・資源更新とCIパイプラインの準備

## 目的

Issue、feature branch、Draft Pull Request、最小PR CIをつなげ、`pr-ci-gate`を初めて成功させる。その成功後にmain branch用RulesetのPhase Bを行い、品質ゲートがmainへのmergeを制御する状態にする。

5.2から5.5までは、ここで作成する同じ変更Issue、同じfeature branch、同じDraft Pull Requestを継続して使用する。

## 開始状態

- 5.1のTemplate作成、Repository設定Phase A、cloneが完了している。
- Repositoryルートで`git status`がcleanである。
- `main-protection`はRequired checkなし、Enforcement `Disabled`で保存されている。
- `.github/workflows/pr-ci.yml`は`workflow_dispatch`だけを持つスターターである。

## 終了状態

- Issue、feature branch、Draft Pull Requestが同じIssue番号で関連付いている。
- 関連情報チェック（`governance-check`）と結果集約（`pr-ci-gate`）を含む最小PR CIがsuccessになっている。
- Test run IDとgovernance証跡Artifactが生成されている。
- `main-protection`へ`pr-ci-gate`がRequired checkとして登録され、Enforcementが`Active`である。

## 1. 変更Issueを作成する

GitHub Web UIで`Issues` → `New issue`を開き、[Issue Form](../../.github/ISSUE_TEMPLATE/change-request.yml)へ次のように入力する。

```text
Title:
[Change]: 最小PR CIを追加する
```
```text
変更の目的:
変更要求とPull Requestを関連付け、CIで変更情報を確認できるようにする。

変更内容:
5.2 patchを適用し、関連情報チェックと結果集約を追加する。

変更対象:
.github/workflows/pr-ci.yml
scripts/pr-ci/
tests/pr-ci/

想定するテスト段階と受入条件:
- governance-checkがsuccessになる
- pr-ci-gateがsuccessになる
- governance証跡Artifactが生成される

target_version:
0.0.0

required_final_stage:
UT

補足・制約:
5.2～5.5で同じIssue、branch、Draft PRを使用する。
```

`target_version: 0.0.0`は、演習開始時点の教材成果物の現在バージョンであり、ルートの`VERSION`ファイルの記載と一致させる。

Issue番号、Test run ID、Environment face ID、Build Artifact IDなどの情報は入力項目ではない。
Issue番号はGitHub、その他のIDはworkflowが生成する。

## 2. feature branchを作成する

Git Bashまたは同等のBashでRepositoryルートへ移動し、`<issue-number>`を作成したIssue番号へ置き換える。
なお、まだ、リポジトリをローカルにCloneしていない場合は、[5.1 ハンズオンの全体像と演習環境の準備](../lessons/5.1-overview-and-setup.md)の操作手順4を実施すること。

```bash
git switch main
git pull --ff-only
git switch -c feature/issue-<issue-number>-pr-ci-foundation
git status
```

branch名のIssue番号は、Pull Request本文の`Closes #<issue-number>`と同じにする。

## 3. 5.2段階patchの役割を確認する

適用前後の違いは次のとおり。

| 状態 | workflowと資源 |
| --- | --- |
| 初期状態 | PR CIパイプライン（`.github/workflows/pr-ci.yml`）は`workflow_dispatch`だけを受け付ける。完成版のjobではない。 |
| 5.2適用後 | PR CIパイプラインを`pull_request`起動へ変更し、関連情報チェック（`governance-check`）、結果集約（`pr-ci-gate`）、Test run ID、governance evidenceの生成・保存処理を追加する。また、関連情報チェックの処理実体（`scripts/pr-ci/governance_check.py`）のテストスクリプト（`tests/pr-ci/test_governance_check.py`）を追加する。 |

5.3以降の静的解析、Go単体テスト、build/package、環境ライフサイクルは、この時点では、まだ追加しない。

## 4. 適用可否、patch、差分を確認する

```bash
git status
bash scripts/exercises/apply-learning-stage.sh --check 5.2
bash scripts/exercises/apply-learning-stage.sh 5.2
git diff --check
git diff
```

`git diff`で、`.github/workflows/pr-ci.yml`、`scripts/pr-ci/governance_check.py`、`tests/pr-ci/test_governance_check.py`だけが5.2の意図どおり変更・追加されていることを確認する。

ローカルにPythonとpytestがある場合は、commit前に次を実行できる。ローカルPythonはハンズオンの必須条件ではないため、最終的な検証はpush後のPR CIで行う。

```bash
python -m pytest tests/pr-ci/test_governance_check.py -q
```

通常の流れは、差分確認、利用可能なテスト、stage、commit、push、Draft Pull Request作成である。

> [!CAUTION]
> 何かしらの事情で、5.2 patchの適用をcommit前に取り消す場合は、以下のコマンドを実行する。通常のNext stepsではない。
>
> ```bash
> git apply -R exercises/5.2/patches/lesson.patch
> ```

patchが適用できない場合は、working treeがcleanか、公開スターターから開始しているかを確認する。[トラブルシューティング](../troubleshooting/README.md)でstage順を確認し、必要な個別ファイルだけを[`reference/completed/`](../../reference/completed/)と比較する。

## 5. 5.2の変更をcommitしてpushする

実際の`git diff --name-only`を確認し、変更したpathだけをstageする。次は標準例であり、実際の差分に応じてpathを調整する。
`<issue-number>`は、作成したIssue番号へ置き換える。

```bash
git status
git add .github/workflows/pr-ci.yml scripts/pr-ci tests/pr-ci
git diff --cached --check
git commit -m "feat: add lesson 5.2 minimal PR CI (#<issue-number>)"
git push -u origin feature/issue-<issue-number>-pr-ci-foundation
```

push後も、後続レクチャー5.3から5.5まで、同じbranchを使う。

## 6. Draft Pull Requestを作成する

GitHub Web UIでpushしたbranchのPull Requestを作成し、`Create draft pull request`を選択する。[Pull Requestテンプレート](../../.github/pull_request_template.md)へ次のように記入する。
`<issue-number>`は、作成したIssue番号へ置き換える。

#### Add a title
```markdown
feat: add section 5 PR CI Pipeline HandsOn (#<issue-number>)
```
#### Add a description
```markdown
## Linked Issue

Closes #<issue-number>

## Change Metadata

target_version: 0.0.0
required_final_stage: UT

## Summary

- Apply Lesson 5.2 patch
- Add governance-check and pr-ci-gate

## Verification

- [ ] governance-check is successful
- [ ] pr-ci-gate is successful
- [ ] governance evidence Artifact is available

## Notes

The same Issue, branch, and Draft Pull Request will be used through Lesson 5.5.
```

`Closes`のIssue番号、branch名のIssue番号、変更Issue番号が一致していることを確認する。
Pull RequestのDraftは5.5まで維持する。

## 7. 最小PR CIとgovernance証跡を確認する

Actionsから、作成したPull Requestの対象workflow runを開き、次を確認する。

- branch名とPull Request本文から同じIssue番号候補を抽出できている。
- Test run IDが`TR-UT-ISSUE-<issue-number>-<workflow-run-id>-A<run-attempt>`形式である。
- 関連情報チェック（`governance-check`）がsuccessである。
- 結果集約（`pr-ci-gate`）がsuccessである。
- Job SummaryにTest run ID、Issue、Pull Request、workflow run/attempt、Artifact名がある。
- `evidence-governance_<test-run-id>`をdownloadできる。

## 8. Artifactを確認する

```text
evidence-governance_<test-run-id>/
├── manifest.json
├── governance-result.json
└── summary.md
```

- `manifest.json`: Test run ID、workflow run/attempt、PR、Issue、Artifact名など、証跡の追跡情報を記録する。
- `governance-result.json`: Issue関連付け、`target_version`、`required_final_stage`、判定結果を機械可読形式で記録する。
- `summary.md`: 同じ判定の人間向け要約と失敗理由を記録する。

Issueを一意に関連付けられない場合、Test run IDは`TR-UT-UNLINKED-<workflow-run-id>-A<run-attempt>`となり、`governance-check`と`pr-ci-gate`はfailureになる。適当なIssue番号で補完せず、branch名とPull Request本文を修正する。

## 9. Repository設定Phase Bを行う

`Checks`タブで初回`pr-ci-gate` successを確認した後、[リポジトリ設定手順](../setup/repository-settings.md)のPhase Bを行う。

```text
Settings
→ Rules
  → Rulesets
    → main-protection
      → Require status checks to pass
        → Show additional settings
        → Add checks
          → pr-ci-gateを検索して選択
        → Require branches to be up to date before merging: 有効
      → Enforcement status: Active
      → Save changes
```

5.2では、`Checks`タブの`pr-ci-gate` success、Rulesetへの登録、Enforcement `Active`までを確認する。Draft状態ではmergeできないため、Conversation画面下部のmerge条件確認は5.5で`Ready for review`へ変更した後に行う。

## 学習上重要なポイント

`pr-ci-gate`は解析やテストを再実行しない。実装済みjobの結果だけを集約し、先行jobがfailure、cancelled、skippedの場合もsuccessにしない。未実装jobを成功扱いにするstubは作らない。

Required checkは`pr-ci-gate`だけにする。branchを最新にする設定により、mainが更新された場合は最新mainを取り込んだ新しいhead SHAでPR CIを再実行してからmergeする。
