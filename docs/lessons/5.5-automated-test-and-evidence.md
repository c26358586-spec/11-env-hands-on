# 5.5 自動テスト・結果証跡管理とCIパイプラインの完成

## 目的

5.4の使い捨てUT環境面へ正式インフラテストと正式APIテストを追加する。テスト結果、ログ、JUnit XML、JSON result、Markdown summary、environment evidence manifestを品質ゲートへ接続し、Ready for review、merge、Issue closeまでを完了する。

5.2で作成した同じ変更Issue、同じfeature branch、同じDraft Pull Requestを引き続き使用する。
本番環境や上位テスト環境へのデプロイ・リリースに向けた、Promotion Candidate Record、Release Candidate登録、Draft Release、GHCR pushは扱わない。

## 開始状態

- 5.4の変更がcommit、push済みで、working treeがcleanである。
- Draft Pull Requestのmetadataは`target_version: 0.0.0`、`required_final_stage: UT`のままである。
- `environment-lifecycle`がBuild Artifactのdownload、UT環境作成、Ansible構成・deploy、起動・疎通確認（readiness check）、cleanup、残存確認、environment証跡uploadを実行できる。

## 終了状態

`environment-lifecycle`が起動・疎通確認（readiness check）後に、事前定義したインフラ9件とAPI 4件の正式テストを実行する。`pr-ci-gate`が正式テスト結果、証跡完全性、cleanup state、残存0件を判定する。

5.2から継続したDraft Pull RequestをReady for reviewへ変更し、最新headと最新mainに対する品質ゲートを確認してmergeする。`Closes #<issue-number>`により変更Issueがcloseされ、feature branchを削除できる。

## 4. 正式テストの役割を確認する

正式インフラテストは、テストケースカタログ（`tests/testcases/README.md`）で事前定義した`INF-001`～`INF-009`をpytest + Testinfraで実行する。UT環境面が期待どおりに構成され、Build Artifact由来のGoアプリが配置・起動されていることを、Docker container/networkとlabel、Nginx設定、binary、実行権限、process、port listen、Nginx経由`/health`などのcase単位で確認する。

正式APIテストは、同じカタログで事前定義した`API-001`～`API-004`をpytest + requestsで実行する。利用者が見るHTTP APIの振る舞いとして、Nginx reverse proxy経由の`/health`、HTTP status、Content-Type、JSON body、Build Artifact version一致、未対応method、未定義path、container直接応答との一致をcase単位で確認する。

各caseは、静的なケースID、automation function、事前定義した期待結果、主な証跡path、skip条件を持つ。正常なLesson 5.5のPR CIでは13件すべてが実行対象であり、`API-004`だけは`TARGET_CONTAINER_NAME`がない場合に条件付きskipする。

各pytest functionは`record_property`で`test_case_id`をJUnit XMLへ記録する。result JSONとテスト別SummaryはJUnit XMLを一度解析した同じ結果から生成し、expected／collected ID、missing／unexpected／duplicate ID、property欠落、Passed／Failed／Errors／Skipped件数、ケースID別結果を保持する。ID不整合、failure、error、skipのいずれかがあれば正式テストを成功扱いにしない。

5.4のreadiness checkは、正式テストを開始できる状態かをfail-fastで確認する前提確認であり、正式テストと重複する確認観点が存在するが、独立して先行確認している。process、port、Nginx経由`/health`、versionを、5.5の正式テストで再確認するのは、受入・回帰証跡としてJUnitへcase単位結果を残すためである。workflow順序とGate条件は変わらない。

## 7. 品質ゲートを確認する

`pr-ci-gate`は、先行jobの結果とoutputsを集約し、少なくとも次を判定する。

- `governance-check`、`static-analysis`、`unit-test`、`build-package`、`environment-lifecycle`がsuccessである。
- 必須証跡ArtifactとBuild Artifactのuploadがsuccessである。
- environment evidence manifestがfinalizeされている。
- `environment_creation_state: Completed`
- `readiness_check_execution_state: Completed`
- `readiness_check_result: Passed`
- `infrastructure_test_result: Passed`
- `api_test_result: Passed`
- `overall_test_result: Passed`
- `missing_evidence_count: 0`
- `environment_evidence_complete: true`
- `cleanup_state`が`Completed`または`CompletedWithWarning`で、`NotAttempted`ではない。
- `remaining_resource_count: 0`

cleanup warningは、使い捨て環境の削除または残存確認で警告があったことを示す。品質処理と正式テストがPassedで、cleanupを試行し、残存0件なら運用上の警告として記録できる。残存がある場合やcleanupを試行できない場合は品質ゲートfailureである。

## 8. Ready for reviewからmerge、Issue closeまで進める

次の順序で5.2から積上げた変更を完了する。

1. 5.5のcommitが同じfeature branch（`feature/issue-<issue-number>-pr-ci-foundation`）へpush済みであることを確認する。
    ```bash
    git fetch origin --prune
    test "$(git branch --show-current)" = "feature/issue-<issue-number>-pr-ci-foundation"
    test "$(git rev-parse HEAD)" = "$(git rev-parse origin/feature/issue-<issue-number>-pr-ci-foundation)"
    ```
    いずれかの`test`が失敗した場合は`Ready for review`へ進まず、現在branch、commit、push先を修正して同じ確認を再実行する。
2. GitHubのPull Request画面で`Ready for review`を選択する。
3. `ready_for_review`イベントで起動した最新PR CIを、Actions画面から開く。
4. `pr-ci-gate`がsuccessであることを確認する。
5. 待機中にmainが更新されている可能性があるためremote refを再取得し、feature branchが最新mainを取り込んでいることを確認する。
    ```bash
    git fetch origin --prune
    git log --oneline HEAD..origin/main  # 何も表示されなければ最新mainを取り込んでいる
    ```
    未取り込みのmain commitが表示された場合だけ、次を実行する。
    ```bash
    git merge --no-edit origin/main
    git push origin HEAD
    ```
    mergeしてpushした場合は、新しいheadで起動したPR CIを待ち、`pr-ci-gate` successを確認し直す。
6. Pull Requestの`Conversation`画面下部で、`pr-ci-gate`とbranch更新を含むRulesetのmerge条件をすべて満たしていることを確認する。
7. Pull Requestをmergeする。
8. Pull Request本文の`Closes #<issue-number>`により、5.2で作成した変更Issueがcloseされたことを確認する。
9. feature branch（`feature/issue-<issue-number>-pr-ci-foundation`）を削除する。

Ready for review後にmainが更新された場合は、再びPR CIが実行されるので、`pr-ci-gate` successを確認し直す。
