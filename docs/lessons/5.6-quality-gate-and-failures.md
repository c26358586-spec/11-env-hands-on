# 5.6 品質ゲートと異常系のハンドリング

## 目的

Goアプリ、IaC、テスト結果・証跡へ演習用patchで意図的な不備を注入し、次を確認する。

- scenarioが期待する層でfailureになる。
- `pr-ci-gate`が不備のある変更のmainへのmergeを止める。
- Job Summaryと証跡から原因を追跡できる。
- patchのrevertまたは不備の修正後にPR CIがsuccessへ戻る。

品質ゲートはPull Request作成を止めるものではない。不備のある変更をmainへmergeしないための判断を行う。

cleanup warningは、使い捨て環境の削除または残存確認で問題が起きた場合の運用上の警告である。cleanupを試行できない状態や残存リソースがある状態を正常化するものではない。

## 開始状態

- 5.5の正常系Pull Requestをmergeし、変更Issueをcloseしている。
- 正常なmainで`pr-ci-gate`がsuccessになる。
- working treeがcleanである。
- scenarioごとに正常なmainから新しいIssue、branch、Pull Requestを作成する。

5.2から5.5のIssue、branch、Pull Requestは使い回さない。5.6はscenarioごとに独立して実施し、次のscenarioも正常なmainから始める。

## 扱うscenario

必須scenarioは次の5件である。

| scenario id | 期待する失敗job／step | 主な確認先 |
| --- | --- | --- |
| `static-analysis-failure` | `static-analysis` / `app-lint` | gofmt log、静的解析result、environment早期cleanup |
| `unit-test-failure` | `unit-test` / `go-unit-test` | Go test log、JUnit XML、単体テストresult |
| `infrastructure-test-failure` | `environment-lifecycle` / `infrastructure-test` | Testinfra log、JUnit XML、API test skip、cleanup |
| `api-test-failure` | `environment-lifecycle` / `api-test` | API test log、JUnit XML、HTTP API不整合 |
| `test-result-evidence-missing` | `pr-ci-gate` / `evidence-completeness` | manifest、欠落証跡数、証跡完全性 |

`cleanup warning`とresidue verification failureは発展scenarioであり、このレクチャーの必須5件には含めない。

## 1. `scenarios.yml`を読む

[scenario定義](../../exercises/5.6/scenarios.yml)で、選ぶscenarioの次のkeyを確認する。

- `id`: コマンドで指定するscenario ID。
- `purpose`: 何を学ぶための不備か。
- `patch`: 適用するpatch path。
- `expected_failure_job`: failureを確認するjob。
- `expected_failure_step`: job内でfailureを確認するstep。
- `evidence_to_check`: 原因と結果を追跡する証跡。
- `expected_gate_result`: `pr-ci-gate`の期待結果。

期待jobだけでなく期待stepも確認し、別の前提不備が先にfailureになっていないことを確認する。

## 2. scenario専用Issueを作成する

GitHub Web UIでscenarioごとに新しいIssueを作成する。次は共通記入例である。`<...>`をscenario定義と実際のpathへ置き換える。

```text
Title:
[Exercise]: <選択したscenarioのtitle>

変更の目的:
<選択したscenarioのpurpose>

変更内容:
<選択したscenarioのpatch>で意図的な不備を注入する。

変更対象:
<選択したscenarioのpatchに記載された、変更ファイルのpath>

想定するテスト段階と受入条件:
- <選択したscenarioのexpected_failure_job>がfailureになる
- <選択したscenarioのexpected_failure_step>のStepがfailureになる
- <選択したscenarioのexpected_failure_step>より前のStepが、failureになっていない
- pr-ci-gateがfailureになる
- <選択したscenarioのevidence_to_check>を確認できる
- 不備の修正後にpr-ci-gateがsuccessになる

target_version:
0.0.1

required_final_stage:
UT

補足・制約:
演習用Pull Requestはmainへmergeしない。
```

例えば、`api-test-failure`のシナリオを選択した場合
```text
Title:
[Exercise]: 正式APIテスト失敗

変更の目的:
正式インフラテストは成功した状態で、API仕様不整合を正式APIテストが検出することを確認する。

変更内容:
exercises/5.6/patches/api-test-failure.patchで意図的な不備を注入する。

変更対象:
- VERSION
- app/health.go
- ansible/infra/roles/nginx/templates/ms1-app.conf.j2

想定するテスト段階と受入条件:
- environment-lifecycleがfailureになる
- api-testのStepがfailureになる
- api-testより前のStepが、failureになっていない
- pr-ci-gateがfailureになる
- 以下を確認できる
  - "evidence-environment_<test-run-id>/summaries/api-test-summary.md"
  - "evidence-environment_<test-run-id>/logs/api-test.log"
  - "evidence-environment_<test-run-id>/test-results/api-test-junit.xml"
  - "evidence-environment_<test-run-id>/test-results/api-test-result.json"
  - "evidence-environment_<test-run-id>/manifest.json"
- 不備の修正後にpr-ci-gateがsuccessになる

target_version:
0.0.1

required_final_stage:
UT

補足・制約:
演習用Pull Requestはmainへmergeしない。
```

## 3. 正常なmainからscenario branchを作成する

Issue番号とscenario IDをbranch名へ含める。

```bash
git switch main
git pull --ff-only
git status
git switch -c feature/issue-<issue-number>-<scenario-id>
```

例えば、Issue番号が#3で、`api-test-failure`のシナリオを選択した場合
```bash
git switch main
git pull --ff-only
git status
git switch -c feature/issue-3-api-test-failure
```

## 4. scenarioのdry-runを行う

scenario一覧を確認し、`--dry-run`で適用の事前確認をする。
dry-runはファイルを変更しない。

```bash
bash scripts/exercises/apply-failure-scenario.sh --list
bash scripts/exercises/apply-failure-scenario.sh --dry-run <scenario-id>
```

## 5. patchを適用してcommit、pushする

```bash
bash scripts/exercises/apply-failure-scenario.sh <scenario-id>
git diff --check
git diff
git add -A
git diff --cached --check
git commit -m "test: exercise <scenario-id> (#<issue-number>)"
git push -u origin HEAD
```

`git diff`では、ルート`VERSION`が`0.0.1`へ更新され、scenario定義が意図する不備とpathだけが変更されていることを確認する。

PushしたfeatureブランチをmainにマージするDraft Pull Requestを作成する。
[Pull Requestテンプレート](../../.github/pull_request_template.md)を使用し、少なくとも次を記載する。

#### Add a title
```markdown

```
#### Add a description
```markdown

- Apply <scenario-id>
- Inject one intentional defect for the failure exercise

## Verification

- [ ] <expected_failure_job> fails at <expected_failure_step>
- [ ] pr-ci-gate fails
- [ ] Expected evidence is available
- [ ] pr-ci-gate succeeds after the repair

## Notes

This exercise Pull Request will be closed without merging.
```

例えば、Issue番号が#3で、`api-test-failure`のシナリオを選択した場合

#### Add a title
```markdown
test: exercise api-test-failure (#3)
```
#### Add a description
```markdown
## Linked Issue

Closes #3

## Change Metadata

target_version: 0.0.1
required_final_stage: UT

## Summary

- Apply api-test-failure
- Inject one intentional defect for the failure exercise

## Verification

- [ ] environment-lifecycle fails at api-test
- [ ] pr-ci-gate fails
- [ ] Expected evidence is available
- [ ] pr-ci-gate succeeds after the repair

## Notes

```

このPull Requestは失敗確認と復旧確認のために使用し、successへ戻った後もmainへmergeせずにCloseする。

## 7. failureと証跡を確認する

Pull Requestを作成すると、PR CIが自動実行され、選択したシナリオに起因してエラーが発生し、pr-ci-gateがfailureになる。

### 異常時の見方

失敗時は、Job Summary（または、`summary.md`）を入口とする。
環境構築や削除に関連する失敗については、`environment-lifecycle-result.json`、該当log、cleanup log、residue verification logで確認する。
正式テスト`Infrastructure test`、`API test`がfailureの場合は、テスト結果サマリ（`summaries/infrastructure-test-summary.md`、`summaries/api-test-summary.md`）から、Failed、またはErrorとなったテストケースとIDを確認する。Failed、またはErrorとなったテストケースについて、その原因をJUnit XML（`test-results/infrastructure-test-junit.xml`、`test-results/api-test-junit.xml`）やテストログ（`logs/infrastructure-test.log`、`logs/api-test.log`）から特定する。

### static-analysis-failure

1. エラーとなったPR CI実行のActions画面で、`pr-ci-gate Summary`から、以下のように`static-analysis job`が失敗したことが分かる
  - Gate result: `failure`
  - governance-check job result: `success`
  - static-analysis job result: `failure`
  - unit-test job result: `success`
  - build-package job result: `skipped`
  - environment-lifecycle job result: `success`
2. `static-analysis Summary`から、以下のように、gofmtのチェックで失敗したことが分かる
  - gofmt: `failure`
  - go vet: `success`
3. また、`static-analysis Summary`の`Failure reasons`から、原因ファイルを特定する（`health.go`に問題があることが分かる）
  - `gofmt is required for: health.go`
4. 証跡Artifact（`evidence-static-analysis_TR-UT-ISSUE-...`）をダウンロードし、`logs/gofmt.log`の`gofmt -l .`対象fileと、続けて記録された`gofmt -d .`の差分hunk、現在行、整形後行から原因箇所を特定する
※ 静的解析failureのためBuild Artifact（`build-go-app_TR-UT-ISSUE-...`）は生成されていないことを確認する

### unit-test-failure

1. エラーとなったPR CI実行のActions画面で、`pr-ci-gate Summary`から、以下のように`unit-test job`が失敗したことが分かる
  - Gate result: `failure`
  - governance-check job result: `success`
  - static-analysis job result: `success`
  - unit-test job result: `failure`
  - build-package job result: `skipped`
  - environment-lifecycle job result: `success`
2. `unit-test Summary`に示された`Evidence Artifact`をダウンロードし、`JUnit XML`に示されたXMLファイルを確認することで、エラーとなったテスト項目と原因を特定する
※ Go単体テストfailureのためBuild Artifact（`build-go-app_TR-UT-ISSUE-...`）は生成されていないことを確認する

### infrastructure-test-failure

1. エラーとなったPR CI実行のActions画面で、`pr-ci-gate Summary`から、以下のように`environment-lifecycle job`が失敗したことが分かる
  - Gate result: `failure`
  - governance-check job result: `success`
  - static-analysis job result: `success`
  - unit-test job result: `success`
  - build-package job result: `success`
  - environment-lifecycle job result: `failure`
2. 続く項目で、以下のように、`Infrastructure test`がFailedとなり、`API test`が`Skipped`されたことが分かる
  - Overall test result: `Failed`
  - Readiness check: `Completed / Passed`
  - Infrastructure test: `Failed`
  - API test: `Skipped`
3. `environment-lifecycle Summary`に示された`Evidence Artifact`をダウンロードし、正式インフラテスト結果サマリ（`summaries/infrastructure-test-summary.md`）から、テストfailureとなったテストケースIDを特定する
4. 正式インフラテストのJUnit XML（`test-results/infrastructure-test-junit.xml`）から、テストfailureとなったテストケースIDを検索し、`failure message`から、原因を特定する
5. 必要に応じて、テストログ（`logs/infrastructure-test.log`）も参照する

### api-test-failure

1. エラーとなったPR CI実行のActions画面で、`pr-ci-gate Summary`から、以下のように`environment-lifecycle job`が失敗したことが分かる
  - Gate result: `failure`
  - governance-check job result: `success`
  - static-analysis job result: `success`
  - unit-test job result: `success`
  - build-package job result: `success`
  - environment-lifecycle job result: `failure`
2. 続く項目で、以下のように、`API test`が失敗したことが分かる
  - Overall test result: `Failed`
  - Readiness check: `Completed / Passed`
  - Infrastructure test: `Passed`
  - API test: `Failed`
3. `environment-lifecycle Summary`に示された`Evidence Artifact`をダウンロードし、正式APIテスト結果サマリ（`summaries/api-test-summary.md`）から、テストfailureとなったテストケースIDを特定する
4. 正式APIテストのJUnit XML（`test-results/api-test-junit.xml`）から、テストfailureとなったテストケースIDを検索し、`failure message`から、原因を特定する
5. 必要に応じて、テストログ（`logs/api-test.log`）も参照する

### test-result-evidence-missing

1. エラーとなったPR CI実行のActions画面で、`pr-ci-gate Summary`から、各種テストはSuccessしているが、`Gate result`だけ失敗していることが分かる
  - Gate result: `failure`
  - governance-check job result: `success`
  - static-analysis job result: `success`
  - unit-test job result: `success`
  - build-package job result: `success`
  - environment-lifecycle job result: `success`
2. 続く項目で、以下のように、欠落した証跡があることが分かる
  - Missing evidence count: `1`
  - Environment evidence complete : `false`
3. `pr-ci-gate Summary`に示された`Evidence Artifact`をダウンロードし、結果集約JSON（`manifest.json`）の、`missing_evidence`の項目から、欠落した証跡ファイルを特定する
4. 結果詳細JSON（`environment-lifecycle-result.json`）の、`evidence_missing_reasons`の項目から、証跡ファイルが欠落した理由を確認する

## 8. 不備を修正する

復旧時もIssueとPull Requestの`target_version`、ルート`VERSION`はすべて`0.0.1`のまま維持する。scenario patch全体を戻すと`VERSION`まで`0.0.0`へ戻り、変更ガバナンスの契約に違反するため、標準の復旧手順には使用しない。

[scenario定義](../../exercises/5.6/scenarios.yml)の`recovery_method`を確認し、注入した不備だけを次のように修正する。

- `static-analysis-failure`: `gofmt -w app/health.go`を実行する。
- `unit-test-failure`: `app/health_test.go`のService期待値2か所を`ms1-broken-api` -> `ms1-go-api`へ戻す。
  - ローカル環境にgoがある場合は、`go -C app test ./...`を実行する。
- `infrastructure-test-failure`: `ansible/infra/roles/nginx/tasks/main.yml`のEnable Nginx reverse proxy siteだけを`state: hard` -> `state: link`へ戻す。
- `api-test-failure`: `app/health.go`へ追加された誤った`/not-found` route（`mux.HandleFunc("/not-found", healthHandler)`の行）と、Nginx template（`ansible/infra/roles/nginx/templates/ms1-app.conf.j2`）へ追加された`location /not-found` のブロックだけを削除する。
- `test-result-evidence-missing`: `scripts/pr-ci/environment_lifecycle.py`へ追加された、API test summaryファイルを削除して欠落を記録するscenario専用処理（`if test_key == "api":`のブロック）だけを除去する。

なお、復旧時もIssueとPull Requestの`target_version`、ルート`VERSION`はすべて`0.0.1`のまま維持する。
scenario patch全体を戻すと`VERSION`まで`0.0.0`へ戻り、変更ガバナンスの契約に違反するため、標準の復旧手順には使用しない。

修正後は`VERSION`が`0.0.1`であり、差分にscenarioで注入した不備が残っていないことを確認する。
```bash
cat VERSION
git diff --check
git diff
```

修正をcommit、pushする。
```bash
git status
git add <修正した不備のファイル>
git diff --cached --check
git commit -m "fix: recover <scenario-id> exercise (#<issue-number>)"
git push
```

最新headのPR CIを待ち、以前failureだったjobと、`pr-ci-gate`がsuccessへ戻ったことを確認する。

## 9. mergeせず演習を終了する

次の順序でscenarioを終了する。

PR CIとpr-ci-gate successを確認
1. Pull Requestをmergeせずclose（`Close pull request`）
2. Issueへ完了コメントを記録
    ```text
    [コメント例]

    異常系演習を完了しました。
    期待したjob／stepのfailureと証跡を確認し、修正後のpr-ci-gate successを確認しました。
    このPull Requestは教材方針によりmainへmergeせずcloseしました。
    ```
3. Issueを手動close
4. remoteとlocalのscenario branchを削除
    ```bash
    git switch main
    git pull --ff-only
    git push origin --delete feature/issue-<issue-number>-<scenario-id>
    git branch -D feature/issue-<issue-number>-<scenario-id>
    ```

他のシナリオを演習する場合は、1に戻り、他のシナリオを選択し、9まで実施する。
