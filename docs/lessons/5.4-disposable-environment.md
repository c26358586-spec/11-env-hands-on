# 5.4 使い捨てテスト環境の構築・デプロイ・疎通確認・削除

## 目的

Terraform Docker Provider、Ansible infra、Ansible deploy、UT環境上の起動・疎通確認（readiness check）、cleanup、残存確認により、使い捨てUT環境面を構築して削除する流れを理解する。

5.2で作成した同じ変更Issue、同じfeature branch、同じDraft Pull Requestを引き続き使用する。5.4のreadiness checkは正式テストそのものではない。正式インフラテストと正式APIテストは5.5で扱う。

## 開始状態

- 5.3の変更がcommit、push済みで、working treeがcleanである。
- `build-go-app_<test-run-id>`を生成し、後続jobへ渡せる。
- Draft Pull Requestのmetadataは`target_version: 0.0.0`、`required_final_stage: UT`のままである。

## 終了状態

GitHub-hosted runner上でUbuntu 24.04 target containerを含むUT環境面が作成される。NginxとGoアプリを構成・デプロイし、Build Artifact由来のGoバイナリへ起動・疎通確認（readiness check）を行った後、cleanupと残存確認を試行する。

Test run IDを生成する仕組みは5.2で追加済みである。Test run ID自体はworkflow runごとに新しく生成され、再実行ではrun attemptを含む新しいIDになる。

## 4. PR CIを確認する

Actionsから、5.2で作成したPull Requestの対象workflow runを開き、次を確認する。

- `environment-lifecycle`がsuccessである。
- `Environment creation state`が、Terraform apply、Ansible infra構成、app deployの完了後にCompletedである。
- `Environment face ID`が`UT-<issue-number>-<workflow-run-id>-A<run-attempt>`形式である。
- `Readiness check`が`Completed / Passed`である。
- `Overall test result`がPassedである。5.4ではreadiness check結果から算出され、個別に任意更新されない。
- `Cleanup state`がCompletedで、`Remaining resource count`が0、`Cleanup warning`がfalseである。
- environment-lifecycleの証跡Artifactが生成されている。
- `pr-ci-gate`が各jobとArtifact uploadを集約してsuccessである。

## 学習上重要なポイント

### Environment face IDとTerraform labels

Environment face IDは、一回のworkflow試行で作成するUT環境面を識別する。run attemptを含むため、再実行時に以前の試行と衝突しない。Terraform labelsはTest run IDとEnvironment face IDをDocker資源へ関連付け、cleanupと残存確認の対象選択に使用する。

### TerraformとAnsibleの責務

Terraformはcontainerやnetworkなど環境面の作成・削除を担当する。Ansible infraはNginxなどインフラ構成、Ansible deployはBuild Artifact由来のGoアプリ配置・起動を担当する。infra構成とapp deployを混同しない。

`environment_creation_state: Completed`はTerraform applyだけの完了を表さず、Ansible infra構成とapp deployまで成功した境界を表す。Ansible infra構成またはapp deployが失敗した場合は`Failed`、deploy後のreadiness checkだけが失敗した場合は環境作成を`Completed`のまま保ち、readinessの失敗として区別する。

### 起動・疎通確認（readiness check）

5.4は、Build Artifactを展開してappを起動でき、process、port、HTTPの最低限の前提が成立し、正式テストを開始してよい状態かを手続き的に確認する。Build Artifact由来のGoバイナリの配置、実行権限、process、port listen、direct HTTP、`/health`のHTTP 200、Nginx経由HTTP、実行中version一致を確認し、前提不成立なら正式テスト前にfail-fastする。

このreadiness checkは正式テストではない。process、port、Nginx経由`/health`、versionは5.5でも確認するが、5.4は正式テスト開始の前提確認、5.5は受入・回帰証跡としての確認であり、目的が異なる。

実行状態は`readiness_check_execution_state`、結果は`readiness_check_result`へ独立して記録する。外部表示の`overall_test_result`をprimaryとし、互換keyの`test_result`はそのaliasとして扱う。

### 早期失敗とcleanup target 0

静的解析、Go単体テスト、build/packageなどで早期失敗し、UT環境を作成しない場合も、`environment-lifecycle`をskipしない。cleanup対象0件としてcleanup手順と残存確認を実行し、残存がなければ`cleanup_state: Completed`とする。cleanup不要を表す別状態は作らない。

cleanupで削除に失敗した場合は`CompletedWithWarning`として警告を記録できるが、cleanupまたは残存確認を実行できない`NotAttempted`は、品質ゲートをfailureとする。

テスト結果・証跡は、Build Artifactへ同梱せず、Test run IDを中心にjobごとのArtifactとして管理する。
