# 5.3 静的解析・単体テスト・ビルド・アーティファクト管理

## 目的

PR CIにGoアプリケーションの静的解析、Go単体テスト、build/package、証跡Artifact、一時Build Artifact、`pr-ci-gate`の集約判定を追加する。変更要求から成果物・証跡までを追跡できる状態にする。

5.2で作成した同じ変更Issue、同じfeature branch、同じDraft Pull Requestを引き続き使用する。新しいIssue、branch、Pull Requestは作成しない。

このレクチャーではGoアプリケーションを扱う。UT環境面は5.4、正式インフラ/APIテストは5.5で扱う。Terraform／Ansible静的解析、Promotion Candidate Record、Release Candidate登録は扱わない。

## 開始状態

- 5.2の変更がcommit、push済みで、working treeがcleanである。
- Draft Pull Requestに`target_version: 0.0.0`と`required_final_stage: UT`がある。
- 関連情報チェック（`governance-check`）、結果集約（`pr-ci-gate`）、governance証跡が動作している。

5.2で設定した`target_version: 0.0.0`とルートの`VERSION`を維持する。レクチャーごとにPull Request本文のmetadataを再入力しない。

## 終了状態

PR CIに`static-analysis`、`unit-test`、`build-package`が追加され、`pr-ci-gate`がjob result、論理結果、必須output、証跡Artifactのupload、一時Build Artifactのuploadを集約する。

このBuild ArtifactはPR CI内で一時利用する`build-go-app_<test-run-id>`であり、Promotion／Releaseで使う正式名称ではない。

## 1. 5.3段階patchの役割を確認する

適用前後の違いは次のとおり。

| 状態 | workflowと資源 |
| --- | --- |
| 初期状態 | PR CIパイプライン（`.github/workflows/pr-ci.yml`）は`workflow_dispatch`だけを受け付ける。完成版のjobではない。 |
| 5.2適用後 | PR CIパイプラインを`pull_request`起動へ変更し、関連情報チェック（`governance-check`）、結果集約（`pr-ci-gate`）、Test run ID、governance evidenceの生成・保存処理を追加する。また、関連情報チェックの処理実体（`scripts/pr-ci/governance_check.py`）のテストスクリプト（`tests/pr-ci/test_governance_check.py`）を追加する。 |
| 5.3適用後 |  PR CIパイプラインに、静的解析（`static-analysis`）、環境を必要としないGoテスト（`unit-test`）、ビルド（`build-package`）の処理を追加する。また、各ジョブの証跡、及び、ビルドアーティファクト（「6. Artifactを確認する」で後述）を、Actions Artifactsに保存する。さらに、各処理の実体（`scripts/pr-ci/static_analysis.py`、`scripts/pr-ci/unit_test.py`、`scripts/pr-ci/build_package.py`）のテストスクリプト（`tests/pr-ci/test_static_analysis.py`、`app/health_test.go`、`tests/pr-ci/test_build_package.py`）を追加する。 |

5.4以降の環境ライフサイクルや、インフラテスト、APIテストは、この時点では、まだ追加しない。

同じfeature branchのRepositoryルートで実行する。

```bash

```

`static-analysis`、`unit-test`、`build-package`と、それぞれの実装・テスト資源が追加されていることを確認する。環境ライフサイクル処理はまだ追加されない。

## 3. 小さなGo単体テストを追加する

5.3 patchによって追加されるGOアプリのテストスクリプト（`app/health_test.go`）に対して、小さなテストを追加する。
追加する小さなテストの例として、既存`healthHandler`が`POST /health`へHTTP 405を返すことを確認する次のテストを追加できる（コードの末尾に追加）。

```go
func TestHealthHandlerRejectsPost(t *testing.T) {
	req := httptest.NewRequest(http.MethodPost, "/health", nil)
	rec := httptest.NewRecorder()

	healthHandler(rec, req)

	if rec.Code != http.StatusMethodNotAllowed {
		t.Fatalf(
			"status code = %d, want %d",
			rec.Code,
			http.StatusMethodNotAllowed,
		)
	}
}
```

この例では既存importの`net/http`と`net/http/httptest`を利用する。追加後は`gofmt`を実行し、差分がこのテストの追加だけであることを確認する。

```bash
gofmt -w app/health_test.go
git diff --check
git diff
```

ローカルにGoがある場合は`go test`を実行できる。ローカルGoは必須条件ではないため、最終確認はpush後のPR CIでも行う。

```bash
cd app
go test ./...
cd ..
```

## 4. 5.3の変更をcommitしてpushする

実際の`git diff --name-only`を確認し、変更したpathだけをstageする。

```bash
git status
git add .github/workflows/pr-ci.yml scripts/pr-ci tests/pr-ci app/health_test.go
git diff --cached --check
git commit -m "feat: add lesson 5.3 Go quality checks (#<issue-number>)"
git push
```

`<issue-number>`は5.2から継続しているIssue番号へ置き換える。5.4に進む前に、このcommitに対する、Draft Pull RequestのPR CIの実行と結果を確認する。

> [!CAUTION]
> 何かしらの事情で、5.3 patchの適用をcommit前に取り消す場合は、以下のコマンドを実行する。通常のNext stepsではない。
>
> ```bash
> git apply -R exercises/5.3/patches/lesson.patch
> ```

適用できない場合は、5.2が適用・commit済みか、working treeがcleanかを[トラブルシューティング](../troubleshooting/README.md)で確認する。

## 5. PR CIを確認する

Actionsから、5.2で作成したPull Requestの対象workflow runを開き、次を確認する。

- `static-analysis`が`gofmt -l .`と`go vet ./...`を実行してsuccessであり、Summaryにはこの2項目だけが表示されている。
- `unit-test`がgotestsumでGo単体テストを実行し、JUnit XMLを生成している。
- `build-package`がGo Linux amd64バイナリを一度だけbuildしている。
- `target_version`、ルート`VERSION`、Build Artifact versionの`X.Y.Z`が一致している。
- 3つの証跡Artifactと一時Build Artifactが生成されている。
- `pr-ci-gate`が各jobとArtifact uploadを集約してsuccessである。

## 6. Artifactを確認する

### 静的解析証跡

```text
evidence-static-analysis_<test-run-id>/
├── manifest.json
├── static-analysis-result.json
├── summary.md
└── logs/
    ├── gofmt.log
    └── go-vet.log
```

`manifest.json`で追跡情報と期待／収集／欠落証跡を、resultとsummaryで判定を、logsで実行結果を確認する。`gofmt -l .`が未整形fileを検出した場合だけ、診断用の`gofmt -d .`が続けて実行され、同じ`gofmt.log`へ対象fileと差分hunkが記録される。`gofmt -d`はfileを書き換えず、resultの`diff_generated`と`diff_returncode`で差分取得結果を確認できる。

### Go単体テスト証跡

```text
evidence-unit-test_<test-run-id>/
├── manifest.json
├── unit-test-result.json
├── summary.md
├── logs/
│   └── go-test.log
└── junit/
    └── go-unit.xml
```

JUnit XMLでtest case単位の結果を確認し、失敗時は`go-test.log`、result、summaryと突き合わせる。

### build/package証跡

```text
evidence-build-package_<test-run-id>/
├── manifest.json
├── build-package-result.json
├── summary.md
└── logs/
    ├── go-version.log
    └── go-build.log
```

buildに使用したGo version、build結果、Build Artifact名、version、checksumへの参照を確認する。

### 一時Build Artifact

```text
build-go-app_<test-run-id>/
├── manifest.json
├── go-app-linux-amd64
└── go-app-linux-amd64.sha256
```

`manifest.json`でsource SHA、version、file情報を、`.sha256`でバイナリのchecksumを確認する。5.4はこのバイナリをdownloadし、再buildせず使い捨てUT環境へ配置する。

## 学習上重要なポイント

Goアプリ単体テストは、入力と期待値、エラー処理、`/health`レスポンス生成ロジック、未対応methodなど、Goコードのロジックをrunner上で検証する。

Go単体テストは、UT環境上のbinary配置、実行権限、process、port listen、Nginx経由疎通を検証しない。これらは5.4の正式テスト開始前の起動・疎通確認（readiness check）と、5.5の正式インフラ/APIテストで確認する。

Build Artifactと証跡Artifactは分離する。Build Artifactにはbinary、checksum、manifestを含め、ログやJUnit XMLはjobごとの証跡Artifactへ保存する。どちらもArtifactへのupload時点から30日保持し（※）、証跡Artifact独自のchecksumは品質ゲート条件にしない。
※証跡ログやテストをパスしたアーティファクトは、もっと長期間保管するのが一般的だが、今回のハンズオン環境の制約上、30日保持としている

`pr-ci-gate`は再build、再テスト、証跡再生成を行わない。先行jobの結果、outputs、Artifact upload結果を集約する。
